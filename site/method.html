Method

A daily-updated public radar of security and safety incidents across embodied robots.

What it is

Robot Security Radar is a daily-updated public radar of security and safety incidents across embodied robots—humanoids, quadrupeds, and consumer/service robots. It is built for buyers: prospective buyers, procurement teams, operators, and anyone evaluating these products. Security researchers and journalists are secondary audiences.

When an incident carries an AI-generated summary, it is clearly labeled on the card and should always be verified against the linked primary source. This site is not security or legal advice. All claims are sourced from publicly available information and should be verified with the linked sources.

How the Radar works

Each day, a pipeline pulls articles from publicly available sources: news outlets, security press, robotics press, communities, and vulnerability databases. A deterministic filter keeps only material that names a specific robot or robot platform together with a security or safety event, and drops stale, drone, industrial-arm, and commentary content. Already-seen and dismissed URLs are removed before any AI processing, so recurring stories cost nothing.

When an AI provider is configured, a screening step discards anything that is not a discrete, verifiable incident—podcasts, opinion pieces, marketing hype, and speculation never pass—and writes a short buyer-facing summary. Without an AI provider, only Items carrying a CVE id can create Incidents; other Items remain in the registry's Wire and are not displayed.

Related Items are clustered into Incidents using exact CVE and vendor/model joins first, then similarity candidates with an optional AI verdict. Status changes require a linked, dated source. A linked vendor advisory page is checked daily: an unchanged page simply advances “last checked”, while a changed page is interpreted only when an AI provider is configured. Results are published as a static site with an RSS feed, updated daily.

Limitations

  • Automated filtering can miss relevant coverage if articles avoid the expected keyword combinations.
  • AI summaries can be wrong. Treat them as a convenience and verify at the linked source.
  • Incident clustering can mis-group articles or create duplicates.
  • Absence of evidence is not proof a vendor has not fixed an issue—a vendor may release a fix that the radar has not yet detected.
  • AI screening, summaries, and advisory-page interpretation are skipped when no provider key is configured. The radar then relies on deterministic joins and CVE evidence, so coverage is narrower.
  • The monitor only checks vendor pages that have been linked to an Incident; a fix published elsewhere can go undetected until the linked page changes.
  • Source feed outages or changes surface as failed pipeline runs visible in the GitHub Actions log.
